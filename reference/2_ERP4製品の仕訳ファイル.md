## 1. 4製品の考え方

#### SAP S/4HANA

勘定タイプで記帳する
明細ごとに「G/L・得意先・仕入先・資産」のどの勘定に記帳するかを表す。総勘定元帳の統制勘定や、利益センタ・セグメントなどはマスタと設定から決まる。
#### Oracle EBS

組合せに記帳する
勘定も部門も、セグメント値の組合せ（勘定科目組合せ）として表す。取引先などの明細は補助元帳が持ち、総勘定元帳は組合せ単位の金額を受け取る。
#### SuperStream-NX

日本型コードで記帳する
勘定科目・補助科目・部門・相手先を、意味の決まったコードとして持つ。分析の切り口は機能コード・プロジェクト・セグメントコードで加える。
#### EXPLANNER/Ax

明細に切り口を積み上げる
振替伝票の明細に、勘定科目・補助科目・部門・取引先と、セグメント管理項目10種を持つ。業務モジュールからの自動仕訳が前提にある。
### 観点ごとの比較

| 観点 | SAP | Oracle EBS | SuperStream-NX | EXPLANNER/Ax |
|---|---|---|---|---|
| ファイルの構造 | ヘッダと明細。BAPIでは明細を勘定タイプ別の構造で渡す 一般仕様 | 明細1行ずつの平坦な表。ヘッダに当たる値も毎行に持ち、取込時にまとめる 一般仕様 | CSVの外部データ取込 確認済／列構成 未確認 | CSVの仕訳取込・自動仕訳 確認済／列構成 未確認 |
| 勘定の表し方 | 勘定タイプ別の勘定（G/L・得意先・仕入先・資産・品目） | セグメントの組合せ全体が1つの勘定 | 勘定科目（最大10桁）＋補助科目 確認済 | 勘定科目＋補助科目 確認済 |
| 管理の切り口 | 意味の決まった項目（原価センタ・利益センタ・セグメントなど）。多くは派生 | 導入先が意味を決めるセグメント（最大30） | 部門・プロジェクト＋機能コード・セグメントコード 確認済 | 部門・プロジェクト＋セグメント管理項目10種 確認済 |
| 取引先 | 仕入先・得意先そのものが補助元帳の勘定 | 総勘定元帳への仕訳には持たない（補助元帳が持つ） | 相手先コードを仕訳に持つ 確認済 | 取引先を仕訳に持ち、取引先元帳で管理 確認済 |
| 税 | 税コードから税明細を自動作成 | 補助元帳（E-Business Tax）で計算し、総勘定元帳では扱わないのが基本 | 未確認（消費税区分を持つと 推定） | 未確認（消費税の集計表があり、税区分を持つと 推定） |
| 日付 | 伝票日付（証憑）と転記日付（会計期間） | 計上日（会計期間） | 未確認 | 未確認 |
| 貸借一致の単位 | 会社コード。伝票分割で利益センタ・セグメントなども | バランシング・セグメント値（会社など） | 未確認 | 部門間は本支店勘定で付替伝票 確認済（部門単位の一致に対応と 推定） |
| 並行会計 | 元帳（主要元帳 0L など）・元帳グループ | 主元帳・副元帳・報告通貨 | 日本基準とIFRSの残高を並行保持 確認済 | 実績・日本基準・IFRS調整などの複数帳簿 確認済 |
| ファイルに入れる量 | 少なめ（マスタ・設定で補う） | 組合せ全体を入れる | 項目ごとにコードを入れる 推定 | 項目ごとにコードを入れる 推定 |

| 関係会社 | 取引先会社 VBUND | 会社間セグメント | 未確認 | 未確認 |
| 税 | 税コード MWSKZ | 補助元帳の税（総勘定元帳では原則扱わない） | 未確認 | 未確認 |

| 摘要 | ヘッダテキスト BKTXT・明細テキスト SGTXT | REFERENCE5（仕訳）・REFERENCE10（明細） | 未確認 | 未確認 |

## 3. SAP S/4HANA

基本の考え方：明細ごとに「どの勘定タイプの、どの勘定に記帳するか」を表す。得意先・仕入先・資産に記帳すると、総勘定元帳の統制勘定は自動で決まり、管理会計の項目（利益センタ・セグメントなど）はマスタと設定から派生する。
### 設計思想

| 考え方 | 内容 |
|---|---|
| 伝票はヘッダと明細 | 1伝票＝ヘッダ1件（BKPF）＋明細n件（BSEG）。伝票番号は「会社コード＋伝票番号＋会計年度」で一意 |
| 会社コードが記帳の単位 | 法人の単位で貸借を一致させる。会社コード間の取引は、各社に明細を立てる会社コード間伝票になる |
| 勘定タイプ | 明細は G/L（S）、得意先（D）、仕入先（K）、資産（A）、品目（M）のいずれか。D・K・A は補助元帳の勘定に記帳する |
| 統制勘定 | 得意先・仕入先はマスタの統制勘定、資産は資産クラスの勘定決定で、総勘定元帳の勘定が自動で決まる。統制勘定へは直接転記できない |
| 未決済明細と消込 | 得意先・仕入先の明細は未決済明細として、支払・入金で消し込む。G/L勘定でも未決済明細管理を設定できる（割当 ZUONR で照合） |
| 管理会計は勘定設定 | 原価センタ・指図・WBSなどを明細に持つ。費用・収益のG/L勘定は管理会計の原価要素を兼ねる |
| 派生 | 利益センタ・セグメント・機能領域は、原価センタや品目などのマスタから派生するのが基本 |
| 伝票分割 | 買掛金・税など貸借対照表の明細にも利益センタ・セグメントを付け、分割特性ごとに貸借を一致させる（ゼロ残高設定）。一致しない分は清算用の明細を自動で作る |
| 税 | 明細の税コードから税額と税明細を自動で作る。税勘定は取引キー（仮払・仮受など）で決まる |
| 必須項目は設定で決まる | 勘定のフィールドステータス、転記キー、管理会計の設定の組み合わせで、項目の必須・任意・非表示が決まる |
| 期間の開閉 | 転記期間バリアントで、勘定タイプ別・勘定範囲別に転記できる期間を開閉する |
| ユニバーサルジャーナル | S/4HANA では FI・CO・資産会計などの明細が ACDOCA にまとまる。元帳 RLDNR ごとに明細を持つ |

### 取込の方法

| 方法 | 特徴 |
|---|---|
| Fiori「仕訳のアップロード」（F2548） | Excel・CSV のテンプレートにヘッダと明細を入れる。借方・貸方は別の列で転記キーは不要。G/L明細が中心で、テンプレートに出る項目はリリース・設定で変わる |
| BAPI_ACC_DOCUMENT_POST | 明細を勘定タイプ別の構造（ACCOUNTGL・ACCOUNTRECEIVABLE・ACCOUNTPAYABLE・ACCOUNTTAX など）で、金額を CURRENCYAMOUNT で渡す。外部システム連携の標準的な方法。標準にない項目は EXTENSION で渡す |
| IDoc（ACC_DOCUMENT） | BAPI と同じ構造を非同期のメッセージで送る |
| バッチインプット（FB01 など） | 画面入力と同じく転記キーで明細を表す。旧来の方法 |

項目の有無・必須は、リリース（オンプレミス／クラウド）、フィールドステータス、伝票分割、派生ルールの設定で変わります。実際の仕様は SE37 の構造定義やテンプレートの出力で照合してください。
## 4. Oracle EBS

基本の考え方：仕訳は「勘定科目組合せ（セグメント値の並び）に、いくら記帳するか」を表す。勘定も部門もセグメントの組合せとして扱い、取引先などの明細は補助元帳が持つ。
### 設計思想

| 考え方 | 内容 |
|---|---|
| 元帳が記帳の単位 | 元帳は勘定体系・会計カレンダー・機能通貨・会計方法の4つで定義される。主元帳のほかに副元帳・報告通貨を持てる |
| 勘定は組合せ | 勘定体系は会計キー・フレックスフィールド。仕訳はセグメント値の組合せ（CODE_COMBINATION_ID）に記帳する |
| セグメントの役割 | クオリファイアで役割を付ける。必須はバランシング・セグメント（会社など）と勘定セグメント。ほかに原価センタ・会社間・管理セグメント |
| バランシング | 仕訳はバランシング・セグメント値ごとに貸借を一致させる。一致しない分は会社間の明細や仮勘定を GL が自動で作る |
| 組合せの統制 | クロス検証ルール（ありえない組合せの禁止）、動的挿入（新しい組合せの自動作成の可否）、セグメント値のセキュリティ |
| 3階層 | バッチ（GL_JE_BATCHES）＞仕訳（GL_JE_HEADERS）＞明細（GL_JE_LINES）。1仕訳は1元帳・1期間・1カテゴリ・1通貨 |
| 取引先は補助元帳 | 仕入先・顧客・資産の明細は AP・AR・FA が持つ。GL は組合せ単位の金額だけを持つ |
| 補助元帳会計（SLA） | 補助元帳の取引から会計ルールで仕訳を作り、詳細または要約で GL へ転送する。GL から補助元帳の明細へドリルダウンできる |
| 実績・予算・予約 | 同じ仕組みで実績（A）・予算（B）・予約（E）を扱う |
| 期間の状況 | 会計期間をオープン・クローズ・将来入力可能などの状況で管理する |

### GL_INTERFACE の構造

明細1件を1行とする平坦な表です。ヘッダに当たる項目も毎行に同じ値を持たせます。仕訳インポートは、元帳・計上日（会計期間）・通貨・仕訳ソース・仕訳カテゴリ・グループID・REFERENCE 列などの値で行をまとめ、バッチと仕訳を作ります。インポート時に、同じ勘定の明細を要約する指定もできます。
### バッチ・仕訳に当たる項目

| 項目 | GL_INTERFACE の列 | 意味・設計上のポイント |
|---|---|---|
| 処理状態 | STATUS | 取込前は NEW。エラー時はエラーコードが入る（必須） |
| 元帳 | LEDGER_ID | 記帳先の元帳。11i の SET_OF_BOOKS_ID に当たる（必須） |
| 実績・予算・予約 | ACTUAL_FLAG | A／B／E（必須）。予算は BUDGET_VERSION_ID、予約は ENCUMBRANCE_TYPE_ID も指定 |
| 計上日 | ACCOUNTING_DATE | この日を含む会計期間に記帳される（必須） |
| 会計期間 | PERIOD_NAME | 予算などで使う。実績は計上日から決まるのが基本 |
| 仕訳ソース | USER_JE_SOURCE_NAME | 仕訳の出どころ。インポート参照の保持、自動転記、承認などを制御（必須） |
| 仕訳カテゴリ | USER_JE_CATEGORY_NAME | 仕訳の種類。自動反転の設定や文書連番の割り当てに使う（必須） |
| 通貨 | CURRENCY_CODE | 入力通貨（必須） |
| グループID | GROUP_ID | 同じソースのデータを取込の単位ごとに分ける |
| バッチ名・摘要 | REFERENCE1 REFERENCE2 | 空欄ならシステムが付ける |
| 仕訳名・摘要 | REFERENCE4 REFERENCE5 | 同上 |
| 仕訳の参照 | REFERENCE6 | 他システムの伝票番号など |
| 反転の指定 | REFERENCE7〜REFERENCE9 | 反転するか、反転する期間、反転の方法（借貸の入替か符号の変更か）。カテゴリの自動反転の設定から決まる運用もある |
| 作成日・作成者 | DATE_CREATED CREATED_BY | 必須 |

伝票番号：GL の仕訳番号は取込時にシステムが付けます。法定の連番が必要な場合は、文書連番を元帳と仕訳カテゴリの組合せに割り当てて採番します。
### 明細の項目

| 項目 | GL_INTERFACE の列 | 意味・設計上のポイント |
|---|---|---|
| 勘定科目組合せ | SEGMENT1〜SEGMENT30 | 勘定体系のセグメント値を定義順に入れる。どの番号が会社・部門・勘定かは導入先ごとに異なる |
| 勘定科目組合せID | CODE_COMBINATION_ID | セグメント値の代わりに組合せIDで指定できる |
| 明細摘要 | REFERENCE10 | 明細の摘要 |
| 明細の参照 | REFERENCE21〜REFERENCE30 | 補助元帳の取引番号などの明細ごとの参照。インポート参照として残せる |
| 統計数値 | STAT_AMOUNT | 数量など金額以外の統計値 |
| 照合参照 | JGZZ_RECON_REF | GL での明細の照合（消込）に使う参照値 |
| 付加情報 | CONTEXT ATTRIBUTE1〜ATTRIBUTE20 | 仕訳明細の付加フレックスフィールド。標準にない情報（取引先コード、証憑日など）を持たせる場合に使う |

### 金額と通貨

| 項目 | GL_INTERFACE の列 | 意味 |
|---|---|---|
| 入力額 | ENTERED_DR ENTERED_CR | 取引通貨の借方・貸方 |

### 税

- 消費税は AP・AR の取引で E-Business Tax が計算し、SLA を通じて GL に記帳するのが基本。GL の仕訳インポートで税を扱うことは少ない
- GL の仕訳に税を持たせる機能もあり、そのための列（TAX_CODE など）がある。使うかは導入の設計による

### 取込の方法

| 方法 | 特徴 |
|---|---|
| 仕訳インポート（GL_INTERFACE） | 外部システムから GL へ入れる標準の方法。表に入れたあと「仕訳インポート」の同時処理プログラムで取り込む。仕訳ソースはユーザー定義のものを使う |
| Web ADI（スプレッドシート） | Excel から入力・アップロード。内部的には同じ仕訳インポートを使う |
| 補助元帳会計（SLA） | 補助元帳の取引から会計ルールで仕訳を作り GL へ転送する。外部の取引を SLA で会計処理する仕組み（会計ハブ）もある |
| 資産の大量追加（FA_MASS_ADDITIONS） | 固定資産の取得を資産データとして FA に取り込む。仕訳は FA と SLA が作る |

## 7. 部門の扱い

部門をひとつの項目として持つか、目的別の別の概念で表すかが、製品の考え方の違いとして最もはっきり出ます。
### SAP：部門は目的別に分ける 一般仕様

| 項目 | 役割 | 部門としての使い方 |
|---|---|---|
| 原価センタ KOSTL | 費用を負担する単位 | 費用の部門。費用の明細にだけ持ち、貸借対照表の明細には持たない。標準階層に必ず属する |
| 利益センタ PRCTR | 損益と一部の貸借対照表を管理する単位 | 事業部・部門別の損益。原価センタから派生。伝票分割を使えば貸借対照表の明細にも付き、その単位で貸借が一致する |
| セグメント SEGMENT | 外部報告の単位 | 部門より大きい事業の単位。利益センタから派生 |

### Oracle EBS：部門はセグメントのひとつ 一般仕様

- 部門は勘定と同格のセグメント（番号は導入先が決める）。原価センタ・セグメントの役割を付けることが多い
- 組合せの一部なので、貸借対照表も損益も全明細が部門の値を持つ。貸借対照表の勘定には共通の値（例：000）を入れる運用もある
- 部門で貸借を一致させたい場合は、部門をバランシング・セグメントにする設計もある
- セグメント値の親子関係で階層を作る。クロス検証ルールで部門と勘定の組合せを、セキュリティで使える部門を制御する

### SuperStream-NX・EXPLANNER/Ax：部門は独立したコード

- SuperStream-NX：部門コードを勘定科目・補助科目・相手先と並ぶ独立した項目として持ち、複数階層で集計する 確認済。貸借対照表の勘定にも持つかは 未確認
- EXPLANNER/Ax：部門を独立した項目として持ち、部門間の取引は本支店勘定で付け替える 確認済。債務も部門別に残高を持つので、部門を貸借も持つ単位として扱える 推定

### 比較

| 観点 | SAP | Oracle EBS | SuperStream-NX | EXPLANNER/Ax |
|---|---|---|---|---|
| 部門に当たる項目 | 原価センタ・利益センタ（目的別） | セグメントのひとつ | 部門コード | 部門 |
| 持つ明細 | 原価センタは費用だけ。利益センタは損益と、伝票分割で貸借対照表も | 全明細 | 未確認 | 損益と貸借対照表 推定 |
| 決まり方 | 原価センタを入力し、利益センタは派生 | 組合せとして入力。補助元帳はルールで決定 | 入力 推定 | 入力 推定 |
| 部門で貸借を合わせる | 利益センタ単位なら伝票分割で可能 | 部門をバランシング・セグメントにすれば可能 | 未確認 | 本支店勘定の付替で対応 |
| 階層 | 原価センタの標準階層、利益センタの階層 | セグメント値の親子関係 | 複数階層 | 未確認 |
